- 상태: Draft
- 작성일: 2026-09-01
- 기준 문서: [SSOT.md](./SSOT.md)
- 2026-09-08 변경: [ADR-0015](./adr/0015-coverage-driven-collection-retrieval.md) A1–A6 승인. 아래 확장 요구는 설계 승인 상태이며 COV 구현·실운영 검증 완료를 뜻하지 않는다.
- 대상 릴리스: MVP

## 1. 제품 요약

Signal Archive는 여러 개발 기술 데이터 소스에서 최근 정보를 수집해 정규화하고, 사용자의 자연어 질문에 기간과 출처가 명시된 기술 트렌드 답변을 제공하는 Intelligence 서비스다.

이 제품이 해결하려는 문제는 “정보를 찾을 수 없음”이 아니라 “서로 다른 신호를 같은 기간과 주제로 묶어, 근거를 확인할 수 있는 설명으로 만드는 데 시간이 많이 듦”이다.

## 2. 목표 사용자

### 2.1 Primary persona

- 새 기술의 도입 여부를 검토하는 백엔드·프론트엔드 개발자
- 기술 방향을 빠르게 파악해야 하는 테크 리드와 엔지니어링 매니저
- 기술 콘텐츠의 주제를 찾는 개발자·기술 블로거

### 2.2 Jobs to be done

- “이번 주에 특정 기술에서 실제로 무엇이 달라졌는지 알고 싶다.”
- “두 기술의 관심 변화가 같은 기간에 어떻게 달랐는지 비교하고 싶다.”
- “요약의 근거가 된 원문과 시점을 직접 확인하고 싶다.”
- “단순 언급량과 제품 업데이트를 구분해 판단하고 싶다.”

## 3. 제품 원칙

1. **출처 우선:** 근거를 연결할 수 없는 핵심 주장은 답변하지 않는다.
2. **시간 우선:** 질문의 기간, 문서의 원 게시 시각, 수집 시각을 구분한다.
3. **신호 구분:** 릴리스, 커뮤니티 언급, 다운로드 등 성격이 다른 지표를 설명 없이 합산하지 않는다.
4. **재현 가능성:** 어떤 문서와 검색 설정이 답변을 만들었는지 추적할 수 있어야 한다.
5. **과장 방지:** 데이터 부족, 편향, 최신성 한계를 답변에 표시한다.

## 4. MVP 사용자 시나리오

1. 사용자가 “최근 7일간 TypeScript 백엔드 분야의 주요 트렌드는?”라고 질문한다.
2. 시스템이 주제, 기간, 질문 의도를 구조화한다.
3. 기간·권리 필터가 적용된 로컬 검색과 coverage 진단을 수행한다. 근거가 부족하면 승인된 source에서 예산·시간 제한 내 원문을 추가 취득하고 저장된 revision/chunk로 재검색한다.
4. 시스템이 주요 흐름, 관찰 근거, 부족 원인과 한계를 답변하고 핵심 주장에 원문 링크·날짜를 붙인다. 제한 내 근거를 확보하지 못하면 보류한다.
5. 사용자는 출처를 열어 답변을 검증한다.

비교 질문에서는 두 대상에 같은 기간·지표 정의·단위를 적용하고, versioned 관측 집합의 공통 target revision과 coverage를 확인한다. 질문 보완 취득을 관심 증가로 합산하지 않으며, 데이터가 없는 축은 0 대신 “데이터 없음”으로 표시한다.

## 5. 기능 요구사항

| ID | 요구사항 | MVP 승인 기준 |
|---|---|---|
| FR-001 | 실제 외부 데이터 수집 | 승인된 서로 다른 유형의 소스 3개 이상에서 예약 수집이 동작한다. |
| FR-002 | 브라우저 수집 | 승인된 소스 1개 이상을 Playwright 수집 어댑터로 처리하거나, 소스 승인이 불가능하면 Playwright E2E 사용과 대체 근거를 ADR에 기록한다. |
| FR-003 | 원본 보존 | 수집 응답, 출처 식별자, 원 URL, 게시·수정·수집 시각, 수집 실행 ID를 추적할 수 있다. |
| FR-004 | 정규화 | 소스별 데이터를 공통 문서·관측값 모델로 변환한다. |
| FR-005 | 중복 제거 | 재수집은 멱등이며 exact duplicate를 새 문서로 발행하지 않는다. near duplicate는 근거를 잃지 않고 묶는다. |
| FR-006 | 임베딩 | 버전이 기록된 임베딩 모델로 검색 단위를 임베딩하고 재처리할 수 있다. |
| FR-007 | 자연어 질의 | 한국어 또는 영어 질문에서 주제, 기간, 의도를 추출한다. |
| FR-008 | 기간 검색 | 명시적 기간을 우선하고, 상대 기간은 요청 시각과 사용자 시간대를 기준으로 절대 UTC 범위로 변환한다. |
| FR-009 | 근거 기반 답변 | 모든 핵심 사실 주장에 하나 이상의 검색된 출처가 연결된다. 근거가 부족하면 답변 범위를 줄이거나 보류한다. |
| FR-010 | 비교 | 동일 기간의 두 기술을 확정된 8개 지표 중 가용한 것끼리 비교하고 지표명과 단위를 표시한다. 단위가 다른 지표를 합산하거나 종합 점수로 만들지 않는다. |
| FR-011 | 출처 표시 | 제목, 게시 시각, 소스명, canonical URL, 해당 주장을 뒷받침한 발췌를 반환한다. 라이선스가 귀속을 요구하는 source는 라이선스 식별자와 귀속 문구를 함께 반환하며, 귀속 정보를 붙일 수 없으면 발췌를 반환하지 않는다. |
| FR-012 | 운영 가시성 | 수집 실행별 성공·실패·처리 건수·지연·재시도 상태를 조회할 수 있다. |
| FR-013 | 실패 복구 | 일시 실패는 제한된 재시도를 하고, 영구 실패는 원인과 재처리 가능 상태를 남긴다. |
| FR-014 | 최신성 표현 | 데이터 최신 시각과 해당 기간의 소스 커버리지를 답변에 표시한다. |
| FR-015 | 과거 수집과 대상 확장 | 지원 capability의 지정 UTC 기간을 checkpoint에서 재개하고, 같은 adapter 유형의 target은 설정 등록으로 추가한다. 초기 horizon 90일은 보존·지출 승인이 아니다. |
| FR-016 | 취득 목적과 관측 집합 | backfill/incremental/on-demand acquisition을 원문과 별도로 보존하고, 버전별 관측 집합·분모·누락을 표시한다. |
| FR-017 | 부족 원인과 제한적 보완 | 원문 부족·처리 미완료·기간 공백·증거 있는 검색 실패/unknown을 구분하고, 외부 취득은 승인된 상한·권리와 저장된 citation을 지킨다. |
| FR-018 | 호출 비용의 재처리 안전성 | 완료 embedding 재사용, 동시 호출 억제, 불명확 outcome 자동 재호출 보류, 재시작에도 유지되는 예산 예약·정산을 제공한다. |

## 7. 성공 지표

### 7.1 제품 지표

- 대표 질문 세트의 task success rate
- 답변별 유효 citation coverage
- 사용자가 원문을 열지 않고도 핵심 변화를 이해할 수 있는지에 대한 수동 평가
- “모름/근거 부족” 판단의 적절성

### 7.2 파이프라인 지표

- 소스별 freshness lag와 collection success rate
- raw → normalized → embedded 단계별 처리량 및 실패율
- exact duplicate 차단률과 near-duplicate cluster 정밀도
- 임베딩 비용과 LLM 답변당 비용
- 주제/기간별 독립 문서·lexical/vector 준비 수, partition 완료/partial coverage, cohort 공통 분모를 별도로 관측한다.
- embedding 완료 재사용·불명확 outcome·예약/정산 비용을 구분한다. 문서/청크 개수 증가만으로 검색 품질 개선을 주장하지 않는다.

## 8. MVP 범위

### 포함

- [SSOT §3.1](./SSOT.md)의 source set을 유지한다. ADR-0015는 새로운 source나 본문 권리를 추가하지 않으며 target별 승인 범위 안에서 확장한다.
- API·피드·브라우저 렌더링 등 복수 수집 방식. source마다 가장 단순하고 정책에 맞는 방식을 고른다
- 예약 수집, 원본 보존, 정규화, 중복 처리, 토픽 태깅, 청킹, 임베딩
- PostgreSQL + pgvector 기반 기간 필터와 하이브리드 검색
- 최근 동향, 특정 기술 업데이트, 두 기술 비교, 많이 언급된 기술 질문
- 출처·게시일·데이터 최신성·한계가 있는 답변
- 단일 사용자 포트폴리오 UI와 운영에 필요한 최소 상태 조회
- Docker 기반 로컬 실행, 자동화 테스트, RAG 평가 세트
- target revision별 90일 초기 backfill, 독립 증분 수집, 검토 기반 대상 발견, 제한된 질문 시점 근거 취득
- lexical/vector readiness 분리, versioned 관측 집합과 coverage 진단, persistent budget 통제

### 제외

- 범용 웹 검색 또는 무제한 크롤러
- 개인화 추천, 알림, 뉴스레터
- 팀·조직·결제·멀티테넌시
- 소셜 로그인과 복잡한 권한 관리
- 모바일 네이티브 앱
- 완전 실시간 스트리밍 수집
- 자동 기술 의사결정 또는 투자 조언
- 자체 모델 학습과 대규모 데이터 웨어하우스

## 9. 주요 제약과 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 소스 이용약관·robots 정책 | 수집 중단 또는 공개 제한 | API/RSS 우선, 소스 승인 체크리스트, Playwright 대상 별도 승인 |
| 소스별 지표 의미 차이 | 잘못된 인기 비교 | 지표별 분리 저장·표시, 무근거 종합 점수 금지 |
| 최신 데이터가 적음 | 환각 또는 과장 | 최소 근거 기준, coverage 표시, 답변 보류 |
| 임베딩·LLM 공급자 변경 | 재임베딩 비용·응답 변경 | provider adapter, 모델 버전 기록, 평가 게이트 |
| near-duplicate 오판 | 근거 손실 또는 이중 집계 | 원본 불변 보존, cluster 방식, 샘플 평가 |
| 동적 페이지 변경 | 브라우저 수집 장애 | semantic locator, fixture contract test, canary와 장애 격리 |

## 10. 미결정 제품 질문

- source별 수집 주기와 schedule 설정값
- 라이선스 귀속을 UI와 API에서 어떻게 표시할지
- 한국어만 지원할지, 질문 언어를 따라 답할지
- 동기 JSON 응답만 제공할지 SSE 스트리밍을 포함할지
- 공개 데모의 인증·사용량 제한 수준
- MVP 품질 임계값과 월간 LLM 비용 상한

확정된 항목은 다음과 같다. 초기 데이터 소스와 Playwright 대상은 [ADR-0004](./adr/0004-initial-data-sources.md)로 확정됐고, "관심"을 어떤 개별 지표로 보여줄지는 8개 지표로 확정됐다. 근거는 [SSOT §3.1·§3.2](./SSOT.md)에 있다.

관련 제안은 [ADR 목록](./adr/README.md), 검증 방법은 [실험 목록](./experiments/README.md)에 기록한다.
